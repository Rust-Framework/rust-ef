# REF v1.6 生产硬化实施计划

## Context（背景）

v1.5.0 完成追踪集成、SemVer 严格化、架构重构后，对 REF 做了五维度生产就绪审计（完整性/安全/性能/稳定/业务覆盖），发现 4 个 P0 阻塞项与 12 个 P1 重要项。根因集中在三处架构缺陷：

1. **连接池每请求新建**——`add_dbcontext` 的 scoped 工厂每请求调用 `DbContext::from_options` → `create_provider` → 工厂闭包新建 Provider+池，跨请求零连接复用，高并发下 DB 握手开销激增、可能耗尽连接数。
2. **行物化全 String 化**——`IAsyncConnection::query` 返回 `Vec<Vec<String>>`，导致 MySQL 每列最多 9 次类型探测、未知类型静默丢数据、大结果集分配爆炸、类型安全丢失。
3. **安全默认明文 + 凭证泄漏**——PG/MySQL `new()` 默认不加密，`DbContextOptions` Debug 直接打印连接串密码。

用户决策：**v1.6 接受破坏性变更**（IFromRow 签名变更等），**TLS 安全优先**（改默认 + 逃生舱）。本计划按 P0→P1 优先级推进全部 16 项，禁用补丁式修改，全部走根因修复。

## 设计要点（已验证）

- **连接池单例**：`DbContextOptions` 新增 `provider_cache: Arc<OnceLock<Arc<dyn IDatabaseProvider>>>`，`create_provider` 用 `get_or_try_init` 建一次共享；`add_dbcontext` 注册时 eager init（fail-fast 启动期），scoped 工厂仅 `Arc::clone`。`IDatabaseProvider` 全 `&self`，跨 DbContext 共享安全。
- **De-String 管道**：`query` → `Vec<Vec<DbValue>>`，`IFromRow::from_row(&[DbValue])` 用 `TryFrom<DbValue>`。前置新增 `TryFrom<DbValue> for i8/u32/u64`。`DbValue` 非 `Hash/Eq`（f64），导航 key 索引保留 `db_value_key -> String`（仅 PK/FK 列，整数/字符串，开销极小）。
- **NULL 语义**：从字符串 `"NULL"` 改为 `DbValue::Null`，多处 `matches!(v, DbValue::Null)`。
- **附带 bug 修复**：字符串 PK include 当前因 `group_rows` 用裸 String 与 `db_value_key` 带引号输出不匹配而失效，De-String 后两侧统一，自然修复。

## 范围与风险

- **最大风险**：M2 De-String 触及 17 处文件 + 9 处测试手动实现，编译错误会级联。缓解：逐层编译（provider→trait→宏→consumer→provider impl→测试），每层定位遗漏。
- **M4.3 嵌套 include 批量化**涉及宏生成代码重构（load_nested_includes），需谨慎保持 ThenInclude 语义。
- **M1.4 TLS 改默认**会破坏现有无 TLS 连接的测试/示例，需逐一改用 `new_insecure`。
- 本计划覆盖审计全部 16 项，按 P0(M1)→根因(M2)→P1 稳定(M3)→P1 性能(M4)→P1 完整(M5)→回归(M6) 推进。
