# REF v1.6 M2 — De-String 物化管道实施计划

## Summary

将物化管道从 `Vec<Vec<String>>` 端到端改为 `Vec<Vec<DbValue>>`。这是 v1.6 的核心架构修复，根因消除四类问题：

1. **MySQL 9x 类型探测**：`cell_to_string` 每个单元格顺序尝试 9 种类型（bool→i64→u64→f64→NaiveDateTime→NaiveDate→Uuid→String→Bytes），性能损耗且类型语义模糊
2. **未知类型静默数据丢失**：MySQL/SQLite 遇到无法识别的类型返回 `"NULL"`，下游误判为 SQL NULL
3. **String 分配开销**：每列读取都经过 `String::to_string()` + `parse()` 往返，整数/浮点/布尔本可直接映射
4. **navigation_loader 二次解析**：`cell_to_db_value` 将 String 再解析回 DbValue，引入 `TypeId` 派发与回退到 `DbValue::String` 的丢失路径

用户已批准：**v1.6 接受破坏性变更**（IFromRow 签名变更）。

## Current State Analysis

### 数据流现状（String 管道）

```
DB Row → provider cell_to_string() → Vec<Vec<String>>
       → IFromRow::from_row(&[String]) → 实体
       → macro generate_scalar_parse: values[i].parse::<T>().unwrap_or(0)
       → navigation_loader: cell_to_db_value(string, TypeId) → DbValue（二次解析）

```

```rust
impl TryFrom<DbValue> for i8 {
    type Error = DbValueConvertError;
    fn try_from(v: DbValue) -> Result<Self, Self::Error> {
        match v {
            DbValue::I16(n) => n.try_into().map_err(|_| DbValueConvertError { source: DbValue::I16(n), target_type: "i8" }),
            DbValue::I32(n) => n.try_into().map_err(|_| DbValueConvertError { source: DbValue::I32(n), target_type: "i8" }),
            DbValue::I64(n) => n.try_into().map_err(|_| DbValueConvertError { source: DbValue::I64(n), target_type: "i8" }),
            DbValue::String(s) => s.parse().map_err(|_| DbValueConvertError { source: DbValue::String(s), target_type: "i8" }),
            other => Err(DbValueConvertError { source: other, target_type: "i8" }),
        }
    }
}

impl TryFrom<DbValue> for u32 {
    type Error = DbValueConvertError;
    fn try_from(v: DbValue) -> Result<Self, Self::Error> {
```

#### 2.2 SQLite sync_ops

**文件**：[crates/sqlite/src/sync_ops.rs](file:///d:/GitCode/RF/rust-ef/crates/sqlite/src/sync_ops.rs)

`query_sync` 返回 `Vec<Vec<DbValue>>`。用 `row.get_ref(i)` 读取 `ValueRef`，按 `ValueRef` 的 `data_type()` 单次派发到原生 `DbValue` 变体（消除 3 次 `or_else` 链）：

```rust
pub(crate) fn query_sync(
    conn: &rusqlite::Connection,
    sql: &str,
    params: &[DbValue],
) -> EFResult<Vec<Vec<DbValue>>> {
    // ... prepare ...
    let rows = stmt.query_map(refs.as_slice(), |row| {
        let mut vals = Vec::with_capacity(cc);
        for i in 0..cc {
            let val = match row.get_ref(i) {
                Ok(rusqlite::types::ValueRef::Null) => DbValue::Null,
                Ok(rusqlite::types::ValueRef::Integer(n)) => DbValue::I64(n),
                Ok(rusqlite::types::ValueRef::Real(x)) => DbValue::F64(x),
                Ok(rusqlite::types::ValueRef::Text(bytes)) => {
                    DbValue::String(String::from_utf8_lossy(bytes).into_owned())
                }
                Ok(rusqlite::types::ValueRef::Blob(bytes)) => DbValue::Bytes(bytes.to_vec()),
                Err(_) => DbValue::Null,
            };
            vals.push(val);
        }
        Ok(vals)
    }).map_err(...)?;
    // ... collect ...
}
```

> SQLite 的 `Integer` 永远是 i64，`Real` 永远是 f64。下游 `IFromRow` 通过 `TryFrom<DbValue>` 将 I64 narrowing 到 i32/i16/i8（`try_into`），F64 → f32 同理。

#### 2.4 MySQL row_conversion

**文件**：[crates/mysql/src/row_conversion.rs](file:///d:/GitCode/RF/rust-ef/crates/mysql/src/row_conversion.rs)

重命名 `cell_to_string → cell_to_db_value`，返回 `DbValue`。仍然按类型顺序探测（sqlx::mysql 不暴露 OID），但直接返回原生 DbValue 而非 String：

```rust
pub(crate) fn cell_to_db_value(row: &sqlx::mysql::MySqlRow, col_idx: usize) -> DbValue {
    if let Ok(v) = row.try_get::<Option<bool>, _>(col_idx) {
        return v.map(DbValue::Bool).unwrap_or(DbValue::Null);
    }
    if let Ok(v) = row.try_get::<Option<i16>, _>(col_idx) {
        return v.map(DbValue::I16).unwrap_or(DbValue::Null);
    }
    if let Ok(v) = row.try_get::<Option<i32>, _>(col_idx) {
        return v.map(DbValue::I32).unwrap_or(DbValue::Null);
    }
    if let Ok(v) = row.try_get::<Option<i64>, _>(col_idx) {
        return v.map(DbValue::I64).unwrap_or(DbValue::Null);
    }
    if let Ok(v) = row.try_get::<Option<f32>, _>(col_idx) {
        return v.map(DbValue::F32).unwrap_or(DbValue::Null);
    }
    if let Ok(v) = row.try_get::<Option<f64>, _>(col_idx) {
        return v.map(DbValue::F64).unwrap_or(DbValue::Null);
    }
    #[cfg(feature = "chrono")]
    if let Ok(v) = row.try_get::<Option<chrono::NaiveDateTime>, _>(col_idx) {
        return v.map(DbValue::NaiveDateTime).unwrap_or(DbValue::Null);
    }
    #[cfg(feature = "chrono")]
    if let Ok(v) = row.try_get::<Option<chrono::NaiveDate>, _>(col_idx) {
        return v.map(DbValue::NaiveDate).unwrap_or(DbValue::Null);
    }
    #[cfg(feature = "uuid")]
    if let Ok(v) = row.try_get::<Option<uuid::Uuid>, _>(col_idx) {
        return v.map(DbValue::Uuid).unwrap_or(DbValue::Null);
    }
    if let Ok(v) = row.try_get::<Option<String>, _>(col_idx) {
        return v.map(DbValue::String).unwrap_or(DbValue::Null);
    }
    if let Ok(v) = row.try_get::<Option<Vec<u8>>, _>(col_idx) {
        return v.map(DbValue::Bytes).unwrap_or(DbValue::Null);
    }
    // 未知类型：tracing::warn!（M3.1 会在此加 tracing 门控的告警）
    DbValue::Null
}
```

> 顺序探测仍保留（sqlx::mysql 的限制），但消除 String 往返。M3.1 会在最后回退前加 `tracing::warn!`。

#### 2.6 PostgreSQL row_conversion

**文件**：[crates/postgres/src/row_conversion.rs](file:///d:/GitCode/RF/rust-ef/crates/postgres/src/row_conversion.rs)

重命名 `cell_to_string → cell_to_db_value`，按 OID 直接返回原生 DbValue 变体：

```rust
pub(crate) fn cell_to_db_value(
    row: &tokio_postgres::Row,
    col_idx: usize,
    pg_type: &PgType,
) -> DbValue {
    use tokio_postgres::types::FromSql;
    match *pg_type {
        PgType::BOOL => {
            let opt: Option<bool> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::Bool).unwrap_or(DbValue::Null)
        }
        PgType::INT2 => {
            let opt: Option<i16> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::I16).unwrap_or(DbValue::Null)
        }
        PgType::INT4 => {
            let opt: Option<i32> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::I32).unwrap_or(DbValue::Null)
        }
        PgType::INT8 => {
            let opt: Option<i64> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::I64).unwrap_or(DbValue::Null)
        }
        PgType::FLOAT4 => {
            let opt: Option<f32> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::F32).unwrap_or(DbValue::Null)
        }
        PgType::FLOAT8 => {
            let opt: Option<f64> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::F64).unwrap_or(DbValue::Null)
        }
        PgType::BYTEA => {
            let opt: Option<Vec<u8>> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::Bytes).unwrap_or(DbValue::Null)
        }
        PgType::TIMESTAMPTZ => {
            let opt: Option<chrono::DateTime<chrono::Utc>> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::DateTime).unwrap_or(DbValue::Null)
        }
        PgType::TIMESTAMP => {
            let opt: Option<chrono::NaiveDateTime> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::NaiveDateTime).unwrap_or(DbValue::Null)
        }
        PgType::DATE => {
            let opt: Option<chrono::NaiveDate> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::NaiveDate).unwrap_or(DbValue::Null)
        }
        PgType::UUID => {
            let opt: Option<uuid::Uuid> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::Uuid).unwrap_or(DbValue::Null)
        }
        // NUMERIC / TEXT / VARCHAR / CHAR / JSON / etc. — String FromSql works
        _ => {
            let opt: Option<String> = FromSql::from_sql_nullable(pg_type, row.get(col_idx)).ok();
            opt.map(DbValue::String).unwrap_or(DbValue::Null)
        }
    }
}
```

> PG 的 NUMERIC 当前返回 String（`rust_decimal` 适配器缺失，见 provider.rs:43-46 注释）。若 `decimal` feature 启用，可在 NUMERIC 分支尝试 `rust_decimal::Decimal` 的 `FromSql`（tokio_postgres 的 `with-rust_decimal_1` feature）。本次先保持 String 回退，M5 再优化。

## Assumptions & Decisions

1. **DbValue 不新增 I8/U32/U64 变体**：SQLite `Integer` 恒为 i64，MySQL/PG 的 i8/u32/u64 通过 I16/I32/I64 widening 承载。下游 `TryFrom<DbValue>` 负责 narrowing。新增变体将引发 6 个 provider 的 type_conversion.rs 全面修改，收益不抵成本。

2. **SQLite `get_ref` 单次派发替代 3 次 `or_else`**：`ValueRef::data_type()` 直接给出 Null/Integer/Real/Text/Blob，无需试错。Integer→I64、Real→F64 是 SQLite 的原生类型，下游 narrowing 由 `TryFrom` 完成。

3. **MySQL 保留顺序探测**：sqlx::mysql 不暴露列 OID（与 tokio_postgres 不同），`try_get::<Option<T>>` 是唯一跨类型方案。但消除 String 往返后，探测成本仅为类型判断（无字符串分配），性能损失可接受。M3.1 会在回退前加 `tracing::warn!`。

4. **PG NUMERIC 暂回退 String**：`rust_decimal::Decimal` 的 `FromSql` 需要 tokio_postgres 的 `with-rust_decimal_1` feature。本次先保持 String 回退（与 v1.5 行为一致），M5 再优化为原生 Decimal。

5. **`db_value_key` 保留**：DbValue 包含 f64/f32，无法 derive Hash/Eq。PK/FK 索引仍需 `DbValue → String` 作为 HashMap key。这是局部索引需求，不影响主物化管道。

6. **`unwrap_or_default` 保持容错语义**：当前 `unwrap_or(0)` 对 parse 失败返回 0，`unwrap_or_default` 对数值类型同样返回 0、对 bool 返回 false、对 String 返回 ""。语义等价，且统一了所有类型的容错模式。

7. **migration 的 `String::try_from` 而非直接 `clone`**：migration 历史 表的 `migration_id`/`product_version` 列在 DB 中是 TEXT/VARCHAR，provider 返回 `DbValue::String`。`String::try_from(DbValue::String(s))` 直接返回 `Ok(s)`，无额外开销。但若 provider 返回非 String 变体（理论上不会），`try_from` 会优雅降级为空串。

8. **`ParseFromDb` 完全删除而非保留兼容**：v1.6 接受破坏性变更。保留 `ParseFromDb` 会导致两套并行的解析路径（String-based + DbValue-based），违背"禁止补丁式修改"原则。
