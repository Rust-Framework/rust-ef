## 二、迭代路线图

### 里程碑总览

```
v1.0 GA ──► v1.1 (查询体验与类型保真) ──► v1.2 (扩展性与性能) ──► v1.3 (生态)
(100%)       (~85%)                       (~95%)                    (100%)
```

| 版本 | 代号 | 核心目标 | 任务数 |
|------|------|---------|:---------:|
| v1.1 | **Query fidelity** | Lazy Loading + PG 原生类型 + CTE/Window + 方言 Bug 修复 + 子查询扩展 | 5 |
| v1.2 | **Scale** | 二级缓存 + 读写分离 + 分库分表 | 3 |
| v1.3 | **Ecosystem** | GraphQL 集成 + 示例扩充 | 2 |

### 范围界定原则

- **v1.1** 聚焦「查询体验」与「类型保真」——用户感知最强，且修复 v1.0 GA 遗留的 PG 方言 Bug
- **v1.2** 聚焦「扩展性」——L2 缓存与读写分离是生产高并发场景的刚需，分片为前瞻性布局
- **v1.3** 聚焦「生态」——GraphQL 集成展示框架可扩展性，附带补充示例项目
- **跨版本原则**：每个版本均保持 100% 向后兼容（v1.0 GA API 冻结），新功能通过可选 feature 或新 trait 引入

## 三、v1.1 迭代计划 — Query fidelity

**目标**: 用户可按需延迟加载导航属性；PostgreSQL 原生类型往返一致；支持 CTE 与窗口函数  
**预期就绪度: ~85%**

### 3.1 Lazy Loading（导航属性延迟加载）

**背景**: 当前 `BelongsTo<T>` / `HasMany<T>` / `HasOne<T>` 是纯数据包装（`relations.rs:20-205`），无 lazy 状态。用户必须显式 `linq!(...; include b.posts)`，遗漏即导致 N+1 或字段为空。EFCore 的 Lazy Loading 是 v1.1 最高优先级特性。

#### 现状（调研结论）

- `NavigationLoader`（`navigation_loader.rs:63-340`）已是批量 IN 查询，**无 N+1 问题**——Lazy Loading 的价值在「按需触发」而非「优化批量」
- 容器 `Clone` 实现始终返回空容器（`relations.rs:55-62, 133-140, 192-199`），隐式「未加载」语义——需显式 `LoadingState` 枚举
- `IDbContext` 是 object-safe（`db_context.rs:443-455`），`provider()` 返回 `&dyn IDatabaseProvider`
- `DbContext.provider: Arc<dyn IDatabaseProvider>`（`db_context.rs:262`），可廉价克隆到 lazy proxy
- `IFromRow::from_row(&[String]) -> EFResult<Self>`（`entity.rs:50-52`）无 provider 注入入口——**核心障碍**
- `NavigationMeta.related_entity_meta: Option<fn() -> EntityTypeMeta>`（`metadata.rs:183`）是函数指针，可复用构造 lazy 子查询

#### 任务

- [ ] **3.1.1 容器类型扩展**（`crates/core/src/relations.rs`）
  - 新增 `LoadingState<T>` 枚举：`NotLoaded` / `Loaded(T)` / `Loading`
  - 扩展 `BelongsTo<T>` / `HasOne<T>` 为 `{ inner: Option<Box<T>>, lazy_ctx: Option<Arc<dyn LazyContext>> }`
  - 扩展 `HasMany<T>` 为 `{ items: Vec<T>, lazy_ctx: Option<Arc<dyn LazyContext>> }`
  - 新增 `LazyContext` trait：`fn provider(&self) -> &dyn IDatabaseProvider; fn owner_keys(&self) -> &[(String, DbValue)]; fn navigation_meta(&self) -> &NavigationMeta;`
  - 保持 `Clone`/`Default`/`Debug` 向后兼容（lazy_ctx 克隆时清空，等同「未加载」）

- [ ] **3.1.2 Lazy 触发器**（`crates/core/src/relations.rs`）
  - `BelongsTo<T>::get(&mut self) -> EFResult<&T>` —— 首次访问时调 `navigation_loader::load_single_reference`
  - `HasMany<T>::items(&mut self) -> EFResult<&Vec<T>>` —— 首次访问时调 `navigation_loader::load_single_collection`
  - `HasMany<T>::is_loaded(&self) -> bool`
  - 触发后状态从 `NotLoaded` → `Loaded`，二次访问直接返回缓存

- [ ] **3.1.3 Provider 注入路径**（`crates/core/src/entity.rs` + `crates/macros/src/entity.rs`）
  - 新增 `ILazyInit` trait：`fn set_lazy_context(&mut self, ctx: Arc<dyn LazyContext>)`
  - `#[derive(EntityType)]` 宏为每个导航字段生成 `set_lazy_context` 实现，构造 `LazyContext` 并注入对应容器
  - `QueryBuilder::to_list`（`query.rs:1349-1374`）物化后，若 `lazy_loading_enabled` 且未 `include`，对每个实体调 `set_lazy_context`
  - 新增 `DbContextOptionsBuilder::use_lazy_loading(bool)`（默认 `false`，opt-in）

- [ ] **3.1.4 NavigationLoader 单实体变体**（`crates/core/src/navigation_loader.rs`）
  - 新增 `load_single_reference(entity: &mut T, nav: &NavigationMeta, provider: &dyn IDatabaseProvider) -> EFResult<()>`
  - 新增 `load_single_collection(entity: &mut T, nav: &NavigationMeta, provider: &dyn IDatabaseProvider) -> EFResult<()>`
  - 复用 `load_scalar_navigation` 的 SQL 构造逻辑（`navigation_loader.rs:150-156, 185-190`），但单实体 IN 退化为 `= ?`
  - M2M 单实体变体复用 `load_many_to_many` 的两阶段查询

- [ ] **3.1.5 循环依赖防护**
  - `LazyContext` 持有 `owner_keys`（所有者主键），触发时构造 `WHERE fk = ?` 单行查询
  - 检测递归深度（thread-local `LazyDepth` counter），超过阈值（如 16）返回 `EFError::Other("lazy loading recursion limit exceeded")`
  - 文档化「禁止在 `Display`/`Debug` 实现中访问导航属性」的约束

- [ ] **3.1.6 集成测试**（`crates/core/tests/lazy_loading_tests.rs`）
  - 不开启 lazy loading：访问导航属性返回空（向后兼容）
  - 开启 lazy loading：首次访问触发查询，二次访问走缓存
  - 嵌套导航（Blog → Posts → Comments）延迟加载
  - 全局查询过滤器与 lazy loading 配合（租户隔离）
  - 递归深度限制触发错误

- 更新 `docs/rust-ef/04-relationships/eager-loading.md` 添加 Lazy vs Eager 对比

### 3.2 PostgreSQL 原生 chrono/uuid 参数绑定

**背景**: 当前 chrono/uuid/decimal 在 `DbValue::From` impl 阶段就坍缩为 `String`（`provider.rs:104-137`），PostgreSQL 未启用 `tokio_postgres` 的 `with-chrono-0_4`/`with-uuid-1` feature，参数绑定走文本通道。v1.0 GA 将此列为 P2 已知限制。

#### 现状（调研结论）

- PostgreSQL provider 用 `tokio_postgres` + `deadpool_postgres`（**不是 sqlx**），`Cargo.toml` 未启用任何类型 feature
- `type_conversion.rs:15` 把 `DbValue::String` 当字符串绑定
- `type_mapping.rs:19` 的 `_ => "TEXT"` 兜底导致建表也建 TEXT 列
- `connection.rs:51` 把每列按 `String` 读出，原生 PG 类型会 `try_get` 失败被静默吞错
- **附带发现**：`HavingExpr::to_sql`（`query.rs:431-468`）硬编码 `?`，LIMIT/OFFSET（`query.rs:611-622`）未走 `gen.pagination()`——均为 PG 方言 Bug

#### 任务

- [ ] **3.2.1 DbValue 新增原生变体**（`crates/core/src/provider.rs`）
  - `#[cfg(feature = "chrono")] DateTime(chrono::DateTime<chrono::Utc>)`
  - `#[cfg(feature = "chrono")] NaiveDateTime(chrono::NaiveDateTime)`
  - `#[cfg(feature = "chrono")] NaiveDate(chrono::NaiveDate)`
  - `#[cfg(feature = "uuid")] Uuid(uuid::Uuid)`
  - `#[cfg(feature = "decimal")] Decimal(rust_decimal::Decimal)`
  - 改写 `From` impl（`provider.rs:104-137`）直接构造新变体，不再坍缩为 String
  - 保持 `DbValue: Clone + PartialEq + Debug`

- [ ] **3.2.2 PostgreSQL Cargo.toml 启用 feature**（`crates/postgres/Cargo.toml`）
  - `tokio-postgres = { version = "0.7", features = ["with-chrono-0_4", "with-uuid-1"] }`
  - 新增 `chrono = "0.4"` / `uuid = { version = "1", features = ["v4"] }` 可选依赖（与 core feature 对齐）

- [ ] **3.2.3 PostgreSQL type_conversion 新增分支**（`crates/postgres/src/type_conversion.rs`）
  - `DbValue::DateTime(dt) => Box::new(dt)`
  - `DbValue::NaiveDateTime(ndt) => Box::new(ndt)`
  - `DbValue::NaiveDate(nd) => Box::new(nd)`
  - `DbValue::Uuid(u) => Box::new(u)`
  - `DbValue::Decimal(d) => Box::new(d)`
  - 保留 `DbValue::String` 兜底分支

- [ ] **3.2.4 PostgreSQL type_mapping 修正 DDL**（`crates/postgres/src/type_mapping.rs`）
  - `"DateTime<Utc>" => "TIMESTAMPTZ"`
  - `"NaiveDateTime" => "TIMESTAMP"`
  - `"NaiveDate" => "DATE"`
  - `"Uuid" => "UUID"`
  - `"Decimal" => "NUMERIC"`

- [ ] **3.2.5 PostgreSQL connection 回读路径**（`crates/postgres/src/connection.rs`）
  - `row.try_get::<_, String>(i)` 改为按列类型分派：chrono 列用 `try_get::<_, chrono::DateTime<Utc>>`，uuid 列用 `try_get::<_, uuid::Uuid>`
  - 或统一序列化为 String 输出给 `IFromRow`（保持下游兼容，但利用原生 `FromSql` 避免静默吞错）
  - 推荐方案：`FromSql` 后立即 `to_string()` / `to_rfc3339()`，保持 `Vec<Vec<String>>` 接口不变

- [ ] **3.2.6 SQLite / MySQL 同步适配**
  - SQLite：`type_conversion.rs:14` 保持 `String` 绑定（SQLite 无原生 TIMESTAMPTZ，TEXT 是正确存储）
  - MySQL：`type_conversion.rs:17` 保持 `String` 绑定（sqlx 的 `with-chrono` feature 可选启用，但 MySQL 的 `DATETIME` 与 String 兼容）
  - DDL 映射保持现状（SQLite `TEXT`，MySQL `DATETIME`/`CHAR(36)`/`DECIMAL`）

- [ ] **3.2.7 集成测试**（`crates/core/tests/extended_types_tests.rs` 扩充）
  - PG 原生 `TIMESTAMPTZ` 列 INSERT + SELECT 往返一致
  - PG 原生 `UUID` 列 INSERT + SELECT 往返一致
  - PG `HAVING COUNT(?) > ?` 占位符修复验证（依赖 3.4.1）
  - 时区处理：`DateTime<Utc>` 入参与出参时区一致

### 3.3 CTE / Window 函数支持

**背景**: 当前 `QueryState`（`query.rs:476-512`）无 `ctes`/`windows` 字段，`LinqClause`（`linq.rs:89-133`）无 `With`/`Window` 变体。复杂分析查询（如「每个部门薪资前 3 的员工」）需退回原始 SQL。

#### 任务

- [ ] **3.3.1 QueryState 扩展**（`crates/core/src/query.rs`）
  - 新增 `ctes: Vec<CteSpec>` 字段，`CteSpec { name: String, columns: Vec<String>, body_sql: String, params: Vec<DbValue> }`
  - 新增 `windows: Vec<WindowSpec>` 字段，`WindowSpec { alias: String, func: WindowFunc, partition_by: Vec<String>, order_by: Vec<Ordering> }`
  - `WindowFunc` 枚举：`RowNumber` / `Rank` / `DenseRank` / `Lag(col, offset)` / `Lead(col, offset)` / `SumOver(col)` / `Custom(expr)`

- [ ] **3.3.2 SQL 拼装扩展**（`QueryState::to_sql_with`，`query.rs:550-625`）
  - WITH 前缀：在第 551 行 `select` 构造之前，若有 `ctes` 非空，拼接 `WITH name1 AS (...), name2 AS (...) `
  - 窗口函数：在第 567-571 行 `projected_columns` 分支，把 `WindowSpec` 转换为 `func() OVER (PARTITION BY ... ORDER BY ...) AS alias` 加入 SELECT 列表
  - 参数索引对齐：CTE body 的参数 index 与主查询连续

- [ ] **3.3.3 linq! 宏扩展**（`crates/macros/src/linq.rs`）
  - `LinqClause` 新增 `With { name, columns, body }` 变体
  - `LinqClause` 新增 `Window { alias, func, partition_by, order_by }` 变体
  - `Parse for LinqInput` 新增解析分支：
    - `with cte_name(columns) { <linq body> }`
    - `window row_number as (partition_by b.dept order_by b.salary desc)`
  - `expand_clauses`（`linq.rs:943-1066`）新增 match 臂：
    - `With` → `.with_internal(name, columns, body_sql, params)`
    - `Window` → `.window_internal(alias, func, partition_by, order_by)`
  - 约束：`with` 子句必须在其他子句之前（解析时单独收集，最后前置）

- [ ] **3.3.4 QueryBuilder 内部方法**（`crates/core/src/query.rs`）
  - `with_internal(name, columns, body_sql, params) -> Self`
  - `window_internal(alias, func, partition_by, order_by) -> Self`
  - 两个方法均 `#[doc(hidden)] pub`，仅宏调用

- [ ] **3.3.5 ISqlGenerator 可选扩展**
  - 评估是否需要 `supports_cte(&self) -> bool`（SQLite 3.8.3+ 支持，PG/MySQL 8+ 支持）
  - 评估是否需要 `supports_window_functions(&self) -> bool`
  - 若需要，加默认实现 `true`（v1.1 目标方言均支持）

- [ ] **3.3.6 集成测试**（`crates/core/tests/cte_window_tests.rs`）
  - CTE 基础：`WITH high_rating AS (SELECT * FROM blogs WHERE rating > 4) SELECT * FROM high_rating`
  - 窗口函数：`ROW_NUMBER() OVER (PARTITION BY blog_id ORDER BY created_at DESC)` 取每组最新 post
  - CTE + 窗口函数组合
  - 三方言验证（SQLite 内存 + PG/MySQL 可选）

### 3.4 HAVING / LIMIT 方言 Bug 修复

**背景**: 调研中发现两处「未走 `gen`」的方言一致性 Bug，影响 PostgreSQL 正确性。虽非 v1.1 新功能，但属 v1.0 GA 遗留缺陷，应随 v1.1 一并修复。

#### 任务

- [ ] **3.4.1 HavingExpr::to_sql 修复**（`crates/core/src/query.rs:431-468`）
  - 函数签名改为 `to_sql(&self, gen: &dyn ISqlGenerator, param_idx: &mut usize) -> String`
  - 第 440 行 `?` 改为 `gen.parameter_placeholder(*param_idx)`，随后 `*param_idx += 1`
  - `And`/`Or`/`Not` 递归调用传入 `gen` 和 `param_idx`
  - 调用点 `having_expr_internal`（`query.rs:1179-1185`）：改为在 `to_sql_with` 阶段延迟编译，或预先传入 gen 和起始 index

- [ ] **3.4.2 to_sql_with LIMIT/OFFSET 修复**（`crates/core/src/query.rs:611-622`）
  - 替换硬编码 `LIMIT x OFFSET y` 为 `gen.pagination(skip, take)`
  - 验证 `gen.pagination()` 三方言实现：
    - SQLite：`LIMIT x OFFSET y`（`sqlite/sql_generator.rs:100-106`）
    - PostgreSQL：`OFFSET x LIMIT y`（`postgres/sql_generator.rs:130-137`）
    - MySQL：`LIMIT x OFFSET y` 或仅 offset 时 `LIMIT 18446744073709551615 OFFSET y`（`mysql/sql_generator.rs:95-102`）

- [ ] **3.4.3 回归测试**
  - PG `HAVING COUNT(id) > ?` 占位符为 `$N`
  - MySQL 仅 offset（无 limit）SQL 合规
  - SQLite/PG/MySQL 三方言 LIMIT/OFFSET 顺序正确

## 四、v1.2 迭代计划 — Scale

**目标**: 二级缓存降低高频读负载；读写分离自动路由读副本；分库分表支持水平扩展  
**预期就绪度: ~95%**

### 4.1 二级缓存（L2 Cache）

**背景**: 当前 `to_list`（`query.rs:1349-1374`）每次都走 DB，无缓存。`ChangeTracker`（`tracking.rs:15-20`）仅元数据，非 identity map。L2 缓存是跨 DbContext 的序列化缓存。

#### 任务

- [ ] **4.1.1 IQueryInterceptor trait**（`crates/core/src/interceptor.rs`）
  - 类比 `ISaveChangesInterceptor`（`interceptor.rs:135-163`）
  - `on_query::<T>(&self, sql: &str, params: &[DbValue]) -> Option<Vec<T>>`（命中缓存返回 Some）
  - `on_query_result::<T>(&self, sql: &str, params: &[DbValue], result: &Vec<T>)`（写入缓存）
  - `on_save_changes(&self, affected_tables: &[&str])`（失效缓存）

- [ ] **4.1.2 CachingProvider 包装器**（`crates/core/src/caching.rs`）
  - 实现 `IDatabaseProvider`，内部持有 `read_provider: Arc<dyn IDatabaseProvider>` + `cache: Arc<dyn Cache>`
  - `Cache` trait：`get(key) -> Option<Vec<u8>>` / `set(key, value, ttl)` / `invalidate_pattern(pattern)`
  - `get_connection` 透传，缓存拦截在 `CachingConnection::query` 层

- [ ] **4.1.3 缓存键设计**
  - `sha256(sql + params + entity_type + tenant_filter)` 作为 key
  - 失效粒度：按表名（`save_changes` 影响的表触发整表失效）
  - TTL 配置（`DbContextOptionsBuilder::cache_ttl(duration)`）

- [ ] **4.1.4 缓存后端**
  - `moka` crate 作为默认内存 LRU 缓存（`moka::future::Cache`）
  - `redis` 可选 feature（`redis::aio::ConnectionManager`）
  - 通过 `Cache` trait 抽象，用户可自定义后端

- [ ] **4.1.5 集成测试**
  - 命中：相同查询二次走缓存
  - 失效：`save_changes` 后缓存失效
  - 多租户：不同租户的缓存隔离
  - 并发：并发查询不重复填充缓存

### 4.2 读写分离自动路由

**背景**: 当前 `DbContextOptions` 单 `provider_factory`（`db_context.rs:58-66`），`IDatabaseProvider::get_connection()` 无 role 提示。

#### 任务

- [ ] **4.2.1 RoutingProvider 包装器**（`crates/core/src/routing.rs`）
  - 实现 `IDatabaseProvider`，持有 `read_provider` + `write_provider`
  - `get_connection()` 根据 task-local `QueryRole` 分发
  - `execute_migration_command` 始终走 `write_provider`
  - `sql_generator()` / `migration_dialect()` 返回 write provider 的（假设同方言）

- [ ] **4.2.2 QueryRole 上下文**
  - `task_local! { static QUERY_ROLE: QueryRole }`，枚举 `Read` / `Write`
  - `DbContext::read_scope<F, Fut, R>(f)` 设置 task-local `Read`，执行闭包
  - `save_changes` / `execute_delete` / `execute_update` 自动设 `Write`
  - `to_list` / `count` / `any` 等读方法默认 `Read`

- [ ] **4.2.3 DI 扩展方法**（`crates/core/src/di.rs`）
  - `use_read_write_split(read_cs, write_cs)` 在 `DbContextOptionsBuilder`
  - 内部构造 `RoutingProvider::new(read_provider, write_provider)`

- [ ] **4.2.4 集成测试**
  - 读查询路由到 read_provider
  - 写操作路由到 write_provider
  - 事务内始终走 write_provider
  - 复制延迟容错（读副本可能滞后，文档化）

### 4.3 数据库分库分表（Sharding）

**背景**: `IDatabaseProvider` 无 shard key 参数；跨 shard 事务不支持（需 xa/2pc，超出 v1.2 范围）。

#### 任务

- [ ] **4.3.1 ShardingProvider 包装器**（`crates/core/src/sharding.rs`）
  - 实现 `IDatabaseProvider`，持有 `shards: HashMap<ShardKey, Arc<dyn IDatabaseProvider>>`
  - `get_connection()` 根据 task-local `ShardKey` 路由
  - `execute_migration_command` fan-out 到所有 shard（广播 DDL）
  - `migration_dialect()` 假设所有 shard 同方言

- [ ] **4.3.2 ShardingStrategy trait**
  - `fn shard_for(&self, table: &str, key: &DbValue) -> ShardKey`
  - 内置 `HashSharding`（`hash(key) % shard_count`）与 `RangeSharding`（按 key 范围）
  - 用户可自定义策略

- [ ] **4.3.3 ShardKey 上下文与路由**
  - `task_local! { static SHARD_KEY: Option<ShardKey> }`
  - `DbContext::shard_scope<F, Fut, R>(shard_key, f)` 设置 task-local
  - `DbSet::query()` 之前显式设置 shard key
  - 未设置时返回 `EFError::Other("shard key required")`

- [ ] **4.3.4 跨 shard 查询限制**
  - 文档化：v1.2 不支持跨 shard JOIN / UNION
  - 跨 shard 聚合需应用层合并（fan-out 查询 + 内存合并）
  - 提供 `DbContext::broadcast_query::<T>(sql, params) -> HashMap<ShardKey, Vec<T>>` 工具方法

- [ ] **4.3.5 迁移自动广播**
  - `ShardingProvider::execute_migration_command` fan-out
  - 每个 shard 独立维护 `__ef_migrations_history`
  - `MigrationEngine::apply` 在 ShardingProvider 上自动广播

- [ ] **4.3.6 集成测试**
  - 单 shard 路由正确
  - DDL 广播到所有 shard
  - 跨 shard 查询返回错误
  - 分片键哈希分布均匀

## 七、风险与应对

| 风险 | 影响 | 概率 | 应对策略 |
|------|:----:|:----:|---------|
| Lazy Loading 容器扩展破坏现有 `Clone`/`Default` 语义 | 向后不兼容 | 高 | 通过 `LoadingState` 枚举保持 `Default::default()` 返回 `NotLoaded`；`Clone` 清空 lazy_ctx（与现有「clone 后未加载」语义一致） |
| Lazy Loading 递归触发栈溢出 | 运行时崩溃 | 中 | thread-local `LazyDepth` counter，超阈值返回错误 |
| PG 原生类型 `FromSql` 与 `Vec<Vec<String>>` 接口不兼容 | 回读路径重构 | 中 | `FromSql` 后立即 `to_string()`，保持下游 `IFromRow` 接口不变 |
| CTE/Window 宏解析复杂度超预期 | v1.1 延期 | 中 | 优先实现 `with` 子句（语法简单），窗口函数可拆至 v1.2 |
| ShardingProvider 跨 shard 事务需求 | 用户期望 xa/2pc | 低 | v1.2 明确文档化「不支持跨 shard 事务」，v1.3+ 评估 |
| 二级缓存失效粒度粗（按表） | 缓存命中率低 | 中 | v1.2 接受按表失效；v1.3 评估按行失效（需 row-level invalidation 协议） |
